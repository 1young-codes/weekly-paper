# Week 13

## Q1. 모델 서빙이란 무엇이며, 왜 필요한가요? 서빙 프레임워크는 어떤 역할을 하나요?

**한 줄 요약:** 모델 서빙은 학습된 모델을 실제 서비스 환경에 배포해 외부 입력에 대한 예측을 실시간으로 제공하는 과정이며, 서빙 프레임워크는 이를 안정적이고 효율적으로 운영하게 해주는 기반 인프라다.

**자세한 설명**

모델 서빙이란
- 학습된 모델을 사용자나 다른 시스템이 쓸 수 있는 형태로 안정적으로 제공하는 과정이다. 모델을 학습시키는 데서 그치지 않고 서빙까지 이어져야 비로소 AI 기술이 제품과 서비스가 된다.

왜 필요한가
1. 학습된 모델은 보통 Jupyter Notebook이나 로컬 환경에서 동작하므로, 그 상태로는 실시간 요청을 처리할 수 없다.
2. 서비스 환경은 다수의 사용자 요청에 대해 높은 안정성과 일관된 응답 속도를 요구하므로, 서빙 전용 시스템이 필요하다.
3. 모델은 계속 업데이트되고 개선되어야 하며, 이 과정에서 새 버전을 무중단으로 교체하고 관리할 수 있어야 한다.

서빙 프레임워크의 역할
- 모델을 메모리에 올려두고 REST API나 gRPC 같은 인터페이스로 외부 요청을 받는다.
- 배치 처리나 비동기 요청 같은 서빙 전략으로 처리 효율을 높인다.
- 로깅과 모니터링으로 모델의 상태와 응답 성능을 실시간으로 추적한다.
- 멀티 모델 로딩, A/B 테스트, Canary 배포 같은 복잡한 운영 전략도 수행한다.

정리하면, 모델 서빙은 AI 모델을 제품 수준의 서비스로 전환하기 위한 핵심 요소이고, 서빙 프레임워크는 이를 실현하는 필수 기반 인프라다.

**예시 / 비유**

- 모델 학습이 뛰어난 요리사를 길러내는 일이라면, 모델 서빙은 그 요리사를 실제 식당 주방에 세워 손님 주문을 받고 일정한 품질로 음식을 내놓게 만드는 일이다. 아무리 실력이 좋아도 주방과 주문 시스템(서빙 프레임워크)이 갖춰지지 않으면 손님에게 음식을 낼 수 없다.

## Q2. Streamlit, FastAPI로 구성된 시스템에 Triton 기반 추론 서버를 통합하려면 어떤 구조로 설계하는 것이 바람직한가?

**한 줄 요약:** 사용자 인터페이스(Streamlit), 애플리케이션 로직(FastAPI), 모델 추론(Triton)의 세 계층으로 역할을 명확히 분리하고, FastAPI가 중간 허브로서 Streamlit과 Triton 사이의 통신을 중계하는 구조가 바람직하다.

**자세한 설명**

계층 1: 사용자 인터페이스 — Streamlit
- 사용자로부터 입력을 받고 결과를 시각적으로 제공한다. 이미지 업로드나 텍스트 입력을 받고, 결과를 그래프나 표로 출력한다.
- 인터랙티브한 프론트엔드 역할에 집중하고, 복잡한 비즈니스 로직은 다음 계층에 위임한다.

계층 2: 애플리케이션 로직 — FastAPI
- 사용자 입력을 받아 전처리하고, Triton 서버에 추론을 요청한 뒤, 응답을 받아 후처리한다.
- Streamlit과 Triton 사이의 중간 허브 역할을 하며, 여러 모델 요청을 통합하고 API 구조를 체계화해 확장성과 유지보수성을 높인다.

계층 3: 모델 추론 — Nvidia Triton Inference Server
- 사전 학습된 모델을 고속으로 추론하기 위한 최적화된 서버다. TensorFlow, PyTorch, ONNX 등 다양한 프레임워크 기반 모델을 동시에 운영할 수 있다.
- FastAPI는 Triton의 REST API나 gRPC 인터페이스를 통해 모델에 요청을 전달하고 응답을 받는다.
- 이 구조 덕분에 모델 서빙과 웹 서버가 서로 독립적으로 운영되어 리소스 분리와 확장이 쉽다.

통신 구조와 이 설계가 바람직한 이유
- 통신 흐름을 한 줄로: 사용자 → Streamlit → (HTTP) → FastAPI → (REST 또는 gRPC) → Triton, 그리고 그 역순으로 응답이 돌아온다. 
- Streamlit이 Triton을 직접 호출하지 않고 굳이 FastAPI를 중간에 두는 이유는 무엇인가? 관심사 분리, 전처리와 후처리의 위치, 인증과 로깅의 집중, 프론트엔드 교체 용이성 등
- 세 계층을 분리하면 확장과 배포 측면에서 구체적으로 무엇이 좋아지는가? (예: 추론 부하가 커지면 Triton만 독립적으로 스케일 아웃, GPU 자원을 추론 계층에만 집중)
- FastAPI와 Triton 사이에서 REST와 gRPC 중 무엇을 언제 선택하는가? 지연 시간, 처리량, 구현 편의성의 trade-off

**예시 / 비유**

식당에 비유하면 Streamlit은 손님을 응대하는 홀, FastAPI는 주문을 정리해 주방에 전달하는 매니저, Triton은 요리를 전담하는 주방이다.
