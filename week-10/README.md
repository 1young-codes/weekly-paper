# Week 10

## Q1. LangChain으로 RAG 시스템을 구축할 때 필요한 주요 구성 요소와 각각의 역할은?

**한 줄 요약:** RAG 시스템은 문서를 불러오고(로더), 조각으로 나누고(분할기), 벡터로 바꿔(임베딩) 저장한 뒤(벡터 저장소), 질문과 관련된 조각을 검색해 프롬프트로 엮고(프롬프트 템플릿), 최종적으로 LLM이 답을 생성하는 일련의 흐름으로 이루어진다.

**자세한 설명**

1. **문서 로더(Document Loader):** PDF, 웹페이지, 텍스트 파일, 데이터베이스 등 다양한 소스에서 문서를 읽어들여 시스템이 다룰 수 있는 형태로 변환한다.
2. **텍스트 분할기(Text Splitter):** 문서가 너무 길면 검색 효율이 떨어지므로 일정 길이의 조각(chunk)으로 나눈다. 각 조각이 임베딩과 검색에 적합한 크기가 되게 한다.
3. **임베딩 모델(Embedding Model):** 문서 조각과 사용자 질문을 숫자 벡터로 변환한다. 이를 통해 의미적 유사도를 계산할 수 있다. OpenAI, Cohere, Hugging Face 등 다양한 옵션이 있다.
4. **벡터 저장소(Vector Store):** 변환된 벡터를 저장하고, 질문이 들어오면 가장 관련 있는 문서 조각을 빠르게 찾아준다. FAISS, Pinecone, Weaviate 등이 대표적이다. 참고로 이 저장소에서 유사도 검색으로 관련 조각을 꺼내오는 인터페이스를 Retriever라고 부른다.
5. **프롬프트 템플릿(Prompt Template):** 검색된 문서 조각과 사용자 질문을 조합해 LLM에 전달할 입력 문장을 구성한다. 이 프롬프트를 어떻게 짜느냐에 따라 생성 품질이 크게 달라진다.
6. **LLM (생성기):** 질문과 관련 문서를 근거로 최종 응답을 생성한다. 이 전체 과정을 Chain 또는 Agent 형태로 묶어 파이프라인이 일관되게 작동하도록 만든다.

정리하면, 문서 로딩, 텍스트 분할, 임베딩, 벡터 저장, 프롬프트 구성, LLM 응답 생성까지 각 구성 요소가 자연스럽게 연결되어야 완성도 높은 응답이 나온다.

**예시 / 비유**

- 도서관에서 사서에게 질문하는 과정과 같다. 사서는 먼저 책들을 주제별로 정리해두고(로딩과 분할과 임베딩과 저장), 질문이 들어오면 관련된 책 몇 권을 뽑아 와(검색), 그 내용과 질문을 함께 놓고 정리한 뒤(프롬프트) 답을 말해준다(LLM 생성). 미리 잘 정리해둘수록 답이 빠르고 정확해진다.

## Q2. RAG 시스템의 성능 평가 방법과 독립 평가 및 종단간 평가의 차이

**한 줄 요약:** RAG 평가는 검색과 생성을 나눠 각 모듈을 따로 재는 독립 평가와, 두 단계를 통합해 최종 응답의 품질을 재는 종단간 평가로 나뉘며, 두 방식은 서로 보완적이다.

**자세한 설명**

독립 평가 (모듈별 평가)
- 각 구성 요소의 성능을 분리해 개별적으로 측정한다.
- **검색기:** 질문에 얼마나 관련 있는 문서를 찾아냈는지를 Precision@k, Recall@k, MRR(Mean Reciprocal Rank) 같은 지표로 평가한다.
- **생성기:** 주어진 문서를 근거로 얼마나 자연스럽고 정확한 응답을 만들었는지를 BLEU, ROUGE, METEOR, BERTScore 등으로 측정한다.
- 시스템 내부의 병목이나 약점을 찾아내는 데 유용하다.

종단간 평가 (End-to-End)
- 검색과 생성을 통합해 전체 시스템이 사용자 질의에 얼마나 잘 응답하는지를 측정한다.
- 정답 일치율(Exact Match), 응답의 유용성, 사실성, 일관성 등을 평가하며, 사람 평가(Human Evaluation)를 병행하는 경우가 많다.
- 최근에는 검색된 근거에 답이 충실한지를 보는 Faithfulness, Groundedness 같은 RAG 특화 지표도 쓰인다.
- 사용자의 실제 경험에 더 가까운 평가 방식이다.

참고: 최근 흐름
- BLEU나 ROUGE처럼 정답 문장과의 표면적 일치를 보는 지표는 RAG 답변 평가에는 한계가 있다고 본다. 그래서 요즘은 LLM을 심판으로 활용하는 방식(LLM-as-a-judge)이나 RAGAS 같은 RAG 전용 평가 프레임워크로 faithfulness와 answer relevance, context precision 등을 재는 것이 실무 표준으로 자리 잡아가고 있다.

**예시 / 비유**

- 독립 평가는 자동차의 엔진과 브레이크를 각각 따로 점검하는 것이고, 종단간 평가는 완성된 차를 실제 도로에서 몰아보며 승차감을 확인하는 것이다. 부품별 점검으로 문제 부위를 찾고, 실주행으로 최종 사용자 경험을 확인한다.

## Q3. RAG 시스템에서 'Agent'란 무엇이며, 어떻게 구현하는가?

**한 줄 요약:** Agent는 고정된 검색-생성 흐름을 따르는 대신, 질문을 해석해 어떤 도구를 언제 쓸지 스스로 판단하고 여러 단계를 유연하게 수행하는 실행 주체다.

**자세한 설명**

무엇인가
- 일반적인 RAG는 질문을 받으면 관련 문서를 검색하고 그 내용으로 답을 생성하는 정해진 구조를 따른다.
- 하지만 어떤 질문은 단순하지 않다. 질문을 쪼개거나, 여러 정보를 종합하거나, 추가 판단이 필요하다. Agent는 이런 경우에 질문의 목적을 이해하고, 어떤 도구를 언제 쓸지 스스로 결정하며, 검색 다음 요약 다음 비교 다음 응답 생성 같은 복합 과정을 단계적으로 수행한다.
- 이렇게 "생각하고(Reasoning) 행동하기(Acting)"를 번갈아 반복하는 동작 원리를 ReAct 패턴이라고 부른다. 도구를 호출해 결과를 관찰하고, 그 결과를 근거로 다음 행동을 다시 판단하는 순환 구조다.

구현에 필요한 요소
1. **언어 모델(LLM):** Agent의 두뇌 역할. 질문을 분석하고 다음 행동을 결정한다.
2. **도구(Tool 또는 Function):** 검색기, 계산기, 데이터베이스 조회기, 요약기 등. Agent는 상황에 따라 이 도구들을 호출해 결과를 얻고 다음 행동으로 이어간다.
3. **메모리(Memory):** 이전 질문이나 중간 결과를 기억해 활용하면 더 일관성 있는 작업이 가능하다.

LangChain에서의 구현
- LangChain은 Agent 구현 기능을 기본 제공한다. LLM과 사용할 도구들을 등록하고 Agent의 동작 방식을 정의하면, 질문에 따라 먼저 검색하고 그 결과를 요약한 뒤 최종 응답을 만드는 식으로 자동 동작하게 만들 수 있다.
- 다만 구체적인 API는 빠르게 바뀌어 왔다. 과거에 널리 쓰이던 `initialize_agent`는 이미 deprecated 되었고, 이후 LangGraph 기반의 `create_react_agent`를 거쳐, 현재 LangChain v1에서는 `langchain.agents`의 `create_agent`가 권장되는 진입점이다. 이 함수는 내부적으로 LangGraph 위에서 동작한다. 따라서 특정 함수 이름보다는 "LLM에 도구와 메모리를 붙여 ReAct 방식으로 동작시킨다"는 개념으로 이해하는 것이 좋다.

정리하면, Agent는 단순한 검색-생성 구조를 넘어 질문을 해석하고 전략을 스스로 선택하며 필요한 작업을 단계적으로 수행하는 유연한 실행 엔진이다. Agent가 들어가면 RAG 시스템은 훨씬 복잡한 질의에도 유연하게 대응할 수 있다.

**예시 / 비유**

- 일반 RAG가 "질문하면 관련 자료를 찾아 읽어주는 사서"라면, Agent는 "리서치를 맡길 수 있는 조수"에 가깝다. 조수는 질문을 받으면 먼저 무엇부터 찾아야 할지 스스로 계획을 세우고, 필요하면 검색과 계산과 요약 같은 도구를 골라 쓰며, 중간 결과를 보고 다음 할 일을 다시 정한다. 정해진 순서를 따르는 것이 아니라 상황에 맞게 판단한다는 점이 핵심이다.
