# Week 11


## Q1. Docker 이미지와 컨테이너의 차이를 설명해보세요.

**한 줄 요약**: Docker 이미지는 변하지 않는 정적인 설계도(템플릿)이며, 컨테이너는 이 이미지를 바탕으로 실제로 동작하는 실행 인스턴스입니다.

**자세한 설명**: 이미지는 애플리케이션 실행에 필요한 코드, 라이브러리, 의존성 등을 모두 포함한 읽기 전용 상태로 어떤 환경에서도 동일한 실행을 보장합니다. 반면, 컨테이너는 이 이미지를 기반으로 생성되어 격리된 환경에서 실행되며, 실행 중 상태가 변하거나 메모리 및 파일 시스템에 변화가 발생할 수 있습니다.

**예시 / 비유**: 이미지가 한 번 만들어지면 변하지 않는 **‘붕어빵 틀(설계도)’**이라면, 컨테이너는 그 틀에 반죽을 넣어 실제로 구워져 나온, 속이나 상태가 변할 수 있는 **‘붕어빵’**입니다.

## Q2. Docker Compose는 어떤 상황에서 유용하며, 일반 Dockerfile과 어떤 차이가 있나요?

**한 줄 요약**: Dockerfile은 단일 컨테이너 이미지를 정의하는 문서이고, Docker Compose는 여러 개의 컨테이너를 한 번에 정의하고 관리하기 위한 도구입니다.

**자세한 설명**: 웹 서버, 데이터베이스, 캐시 서버 등 여러 서비스가 함께 작동해야 하는 실제 애플리케이션 환경에서 Dockerfile만으로는 각각의 컨테이너를 일일이 실행하고 연결하기 번거롭습니다. Docker Compose를 사용하면 `docker-compose.yml` 파일 하나에 서비스 간의 네트워크 연결, 볼륨 공유, 실행 순서 등을 정의하여 복잡한 멀티 컨테이너 환경을 효율적으로 일괄 실행하고 관리할 수 있습니다.

**예시 / 비유**: Dockerfile이 한 명의 배우가 입을 의상과 대본을 적어둔 **‘캐릭터 설정집’**이라면, Docker Compose는 여러 배우가 무대 위에서 언제 어떻게 상호작용할지 지휘하는 **‘연극의 총괄 대본(디렉팅)’**입니다.

## Q3. Kubernetes의 기본 개념은 무엇이며, Docker와는 어떤 관계가 있나요?

**한 줄 요약**: Docker는 개별 컨테이너를 만들고 실행하는 '생성 도구'이며, Kubernetes는 다수의 컨테이너를 대규모로 자동 배포 및 관리하는 '오케스트레이션 시스템'입니다.

**자세한 설명**: 다수의 컨테이너가 얽혀 있는 실제 운영 환경에서는 컨테이너의 상태나 상호작용을 수동으로 관리하기 어렵습니다. Kubernetes는 컨테이너를 클러스터와 Pod 단위로 묶어 배포하고, 장애 발생 시 자동 재시작 및 노드 재배치를 수행합니다. 또한 자동 확장, 로드 밸런싱, 롤링 업데이트 등의 고급 기능을 통해 대규모 분산 환경을 안정적으로 운영할 수 있게 해줍니다.

**예시 / 비유**: Docker가 뛰어난 연주자를 훈련시키고 악기를 쥐여주는 **‘음악 학교’**라면, Kubernetes는 수백 명의 연주자가 조화롭게 교향곡을 연주할 수 있도록 지휘하고 문제가 생긴 연주자를 즉시 교체해주는 **‘오케스트라 지휘자’**입니다.

## Q4. 딥러닝 모델을 ONNX, TensorRT 등의 포맷으로 변환해야 하는 이유는 무엇인가요?

**한 줄 요약**: 학습된 딥러닝 모델을 실제 서비스 환경에 맞춰 '범용성(ONNX)'을 확보하고, '추론 속도 최적화(TensorRT)'를 달성하기 위해 포맷을 변환합니다.

**자세한 설명**: PyTorch 등 특정 프레임워크로 학습한 모델은 플랫폼 의존성이 높습니다. 이를 프레임워크 독립적인 ONNX 포맷으로 변환하면 다양한 환경(TensorFlow, Caffe2 등)에서 동일하게 재활용할 수 있습니다. 나아가 NVIDIA의 고속 추론 엔진인 TensorRT로 변환하면 GPU 연산이 최적화되어 지연 시간(latency)이 단축되고, 서비스 배포 효율성이 극대화됩니다.

**예시 / 비유**: PyTorch 모델이 특정 지역에서만 통하는 **‘사투리’**라면, ONNX는 누구나 이해할 수 있는 **‘표준어’**로 번역하는 과정입니다. 그리고 이를 TensorRT로 바꾸는 것은, 그 표준어 대본을 훈련된 전문 아나운서가 가장 빠르고 명확하게 읽어주는 것(속도 최적화)과 같습니다.

## Q5. 양자화 기법인 Post-Training Quantization과 Quantization-Aware Training의 차이를 설명해보세요.

**한 줄 요약**: PTQ는 학습이 모두 끝난 후 모델을 양자화하여 '빠르고 간편하게' 경량화하는 방식이고, QAT는 훈련 단계부터 양자화 손실을 시뮬레이션하여 '정확도 저하를 최소화'하는 방식입니다.

**자세한 설명**: 두 기법 모두 모델의 가중치를 float32에서 int8 등의 낮은 정밀도로 변환해 추론을 가속합니다. PTQ(사후 양자화)는 추가 학습 없이 즉시 적용할 수 있어 편리하지만 모델 정밀도 하락으로 인한 성능 저하 위험이 있습니다. 반면 QAT(양자화 인지 학습)는 학습 과정에서 양자화 시의 오차를 미리 반영하여 보정하므로, 시간과 리소스가 더 들지만 PTQ에 비해 원본의 높은 정확도를 안정적으로 유지할 수 있습니다.

**예시 / 비유**: PTQ는 다 완성된 고화질 사진을 급하게 저해상도로 압축하는 것(빠르지만 깨질 수 있음)이고, QAT는 처음부터 작은 캔버스(저해상도)에 그려질 것을 고려해 선명도를 조절해가며 밑그림부터 그리는 것(수고롭지만 결과물이 깔끔함)입니다.

## Q6. 양자화나 모델 경량화 후 실제 서비스에서 성능이 저하되지 않도록 하기 위해 어떤 테스트나 확인 절차가 필요할까요?

**한 줄 요약**: 동일 데이터셋을 통한 원본과의 '정확도 오차 비교', 프로파일링 툴을 활용한 '자원 및 지연 시간(latency) 측정', 그리고 실제 트래픽 기반의 'A/B 테스트'를 종합적으로 거쳐야 합니다.

**자세한 설명**: 경량화 후 속도는 빨라졌으나 정확도가 크게 훼손되는 것을 막기 위한 필수 검증 단계입니다. 첫째, 동일한 테스트 데이터셋으로 Top-1 accuracy 등 지표 하락폭이 허용 범위 내인지 점검합니다. 둘째, trtexec(TensorRT) 등의 도구로 실제 추론 속도, 메모리 사용량, GPU 활용률을 벤치마킹합니다. 셋째, Shadow testing이나 A/B 테스트를 통해 실제 사용자 트래픽 환경에서 예상치 못한 병목이나 성능 예외 상황이 없는지 모니터링하여 안정성을 확보합니다.

**예시 / 비유**: 경주용 자동차의 부품을 가벼운 소재로 교체(경량화)한 후, 1) 부품의 내구도를 기존과 비교(정확도 테스트)하고, 2) 트랙에 올려 최고 속도를 측정(벤치마크)한 뒤, 3) 실제 레이스 환경과 똑같이 모의 주행(A/B 테스트)을 해보며 안정성을 종합 검증하는 것과 같습니다.
